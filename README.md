# uptime

站点可用性监控。**Cloudflare Workers + D1 + Globalping**，零 npm 依赖、零构建步骤，
`npx wrangler deploy` 直接上线。

- 前台：总览页（分组 + 30 天色条 + 证书剩余天数）、单站点详情页（延迟趋势、故障记录）
- 后台：左右两栏管理（左分类、右站点），分类与站点都可拖拽排序，需管理员密码登录
- 探测：Globalping 的**第三方真实探针**（含中国大陆节点），而不是 Cloudflare 边缘直连 ——
  后者从机房出网，测不到"大陆用户实际访问有多快"

---

## 部署

D1 数据库的**创建、绑定、建表都由 `scripts/setup-d1.mjs` 自动完成**——
不需要手工 `d1 create`、不需要复制 `database_id`、不需要单独跑建表。
脚本是幂等的：库已存在就复用，多次执行不会产生副作用。

**建表这一步连脚本都不需要**：Worker 在第一次请求时会自己检查库结构，缺表就按
`schema.sql` 建好、把版本号写进 `meta`。所以不管你怎么部署（CLI、控制台连 GitHub、
Dashboard 里贴代码、CI），**部署完打开页面就是能用的**，不会出现「部署成功但接口全报
`no such table`」。详见 [库结构自举](#库结构自举为什么建表不靠命令)。

**域名不由脚本绑定**，你在 Cloudflare 控制台自己绑（见第 1 步）。这样换域名不必改仓库、
也不必重新部署。

需要你自己做的只有两件事：**绑域名**、**设管理员密码**。

### 1. 授权 + 绑定域名

```bash
npx wrangler login          # 首次需授权 Cloudflare 账号
```

`wrangler.toml` 里**刻意不写 `[[routes]]`**：域名不跟着配置走，避免每次部署都用配置去
覆写 DNS 与证书。绑定一次性敲定后长期有效：

> **Workers & Pages → 选中本项目 Worker → Settings → Domains & Routes → Add → Custom domain**

> ⚠️ 不要只依赖 `workers.dev` 域名 —— 实测在中国大陆不可达。
> 之所以保留了 `workers_dev = true`：绑域名之前总得有个能自检的地址。

### 2. 设置管理员密码

密码**只来自环境变量** `ADMIN_PASSWORD`，后台没有改密码的入口（改密码 = 改这里）。

**必须在部署前设好** —— 鉴权是 fail-closed：没配这变量时后台**整体停用**
（打开 `/admin` 只会看到「后台已停用」的说明页，所有后台接口一律 403）：

```bash
npx wrangler secret put ADMIN_PASSWORD
```

用 GitHub 自动部署（Workers Builds）的话在 Dashboard 配一次：

> **Workers & Pages → 选中本项目 → Settings → Variables and Secrets → 添加**
> 名称填 `ADMIN_PASSWORD`，**类型必须选 Secret**（不是 Text），保存。
> 之后每次部署都会自动注入，无需重复配置。

> ### ⚠️ 为什么必须选 Secret —— 实测踩过的坑
> `wrangler deploy` 会把「版本的全部明文变量」按本地配置重写，所以
> **只在控制台填的明文（Text）变量，会在下一次部署时被整个清掉**
> （以 `wrangler.toml` 为准，`[vars]` 里没有的就视为"已删除"）。
>
> 症状很有迷惑性：变量明明填了，但 Worker 运行时读不到，打开 `/admin` 只会看到
> 「后台已停用 · 未设置管理员密码」——看起来像代码 bug，其实是变量被部署清空了。
> （fail-closed 的好处就在这里：配置丢了是"用不了"，而不是"谁都能用"。）
>
> | 类型 | 设置方式 | 重部署后是否保留 |
> |---|---|---|
> | Secret | 控制台或 `wrangler secret put` | ✅ 永远保留 |
> | 明文 Variables | 仅控制台填 | ❌ 会被清掉 |
> | 明文 Variables | 写进 `wrangler.toml` 的 `[vars]` | ✅ 随部署生效 |
>
> 本项目已在 `wrangler.toml` 里设了 **`keep_vars = true`**，让 wrangler 不去动
> 控制台上的变量；但**敏感值仍然推荐用 Secret**（值不会明文可见，也不进代码库）。

> **为什么不做成"没设密码就先开放后台"**：那样等于用一个 5 秒就消失的提示，
> 去兜住"任何人打开这个网址都能改配置、读到 Globalping Token"这件事。
> 注意 `/admin` 这个 HTML 是静态资源，由 Assets 直接返回、根本不经过 Worker，
> 拦不住也没必要拦 —— 页面里只有空壳，数据一个字段也拿不到。
>
> **为什么不做成"首次打开时让你设一个密码"**：那个接口本身就没有鉴权，
> 谁先打开谁就能把密码设成自己的，反过来把主人锁在外面。
>
> **为什么不做成后台可改**：那样就得在 D1 里存密码哈希，还要额外处理「改密码如何
> 作废旧会话」。而密码本质是部署期配置，放环境变量更简单、也更容易审计。
> 改密码的代价就是重新设置一次变量，不需要重新部署。

### 3-A. 命令行部署（一条命令）

```bash
npm run deploy
```

这个命令做四件事，然后才 `wrangler deploy`：

1. 列出账号下的 D1，按名字找 `uptime-db`
2. **没有就创建**，并把 `database_name` 与 `database_id` **写回 `wrangler.toml`**（即自动绑定）；
   已有则校验配置与实际是否一致，不一致就修正
3. 执行 `schema.sql` 建表
4. **校验表结构与 `schema.sql` 一致**，不一致就中止部署

全过程幂等，反复跑不会重复建库。

> 第 3、4 步是**提前把问题暴露在部署阶段**，不是功能前提 —— 就算跳过它们，
> Worker 第一次请求时也会自己把表建好（见下文「库结构自举」）。
> 保留它们的价值在于：结构缺列这种事在部署日志里一行就能看到，
> 而不是等到线上某个接口报 `no such column`。

> 加字段怎么办：改 `schema.sql`，把顶部的 `-- schema-version:` 加 1，
> 并在 `src/migrations.js` 里补一条 `ALTER TABLE ... ADD COLUMN`。
> 新库直接按完整定义建；已经跑了一段时间的旧库靠那条迁移自动补列，
> 不需要重建、不会丢数据。详见 [改表结构](#改表结构)。

> ⚠️ **`wrangler.toml` 里的 `database_id` 不要提交**：第 2 步写回去的是**本机账号的实际
> uuid**，只对当前账号有效。跑完 `setup` / `deploy` 后 `git status` 里 `wrangler.toml` 会
> 显示为已改动 —— 把它还原成空值 `""` 再提交（本仓库里它就是空的）。
> 脚本只认 `database_name`、不认已有 uuid，留空才能保证换账号/换环境时**自动对齐**；
> 一旦提交上去，就等于固化了一个只对某次部署有效的值，换环境必然指向不存在的库。

> 只想做数据库准备、不部署：`npm run setup`
>
> 换库名：`D1_NAME=my-db npm run deploy`；换 D1 主区域：`D1_LOCATION=wnam npm run deploy`。

### 3-B. 连接 GitHub，推送即部署

在 Cloudflare Dashboard 操作（只需配一次）：

1. **Workers & Pages** → **Create** → 切到 **Import from Git** 标签
2. 授权 GitHub，选中本仓库（若没看到，点 *Configure GitHub app* 调整仓库可见范围）
3. 构建配置：

   | 项 | 值 |
   |---|---|
   | Framework preset | **None** |
   | Build command | 留空（本项目无构建步骤） |
   | **Deploy command** | **`npm run deploy`** |
   | Root directory | `/`（若本项目在仓库子目录里，填子目录名） |

4. 保存即触发首次部署；此后**每次 `git push` 到 `main` 都会自动部署**

> ⚠️ 推荐填 `npm run deploy`：它会先建库、把 `database_id` 写回配置。**全新环境**上
> 少了这一步，`wrangler deploy` 会因为绑定指向空 uuid 而失败。
>
> 已经手工建好库、`database_id` 也填过的话，填 `npx wrangler deploy` 同样能跑起来 ——
> **建表不依赖这条命令**，Worker 首次请求会自己补（见「库结构自举」）。
> 区别只在暴露时机：缺列这类结构问题会在运行时才报错，而不是在部署日志里停下来。
>
> 生产分支默认 `main`。不同则在 Settings → Builds 改 *Production branch*。
> CI 环境由 Cloudflare 自动注入 `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID`，不需要配密钥。

### 4. 首次访问

访问 `https://<你的域名>/admin` 登录后台，密码就是第 2 步设的 `ADMIN_PASSWORD`
（30 天免登录，Cookie 为 `HttpOnly + SameSite=Lax + Secure`）。

**第一次打开时库是空的，页面会顺手把它建好** —— 不需要预先跑任何命令。
这一步（最多十几条 DDL）只在首次请求发生一次，之后再也不会执行。

没设过密码变量的话，这个页面只会显示「后台已停用」与设置步骤 —— 照上面的步骤补上再刷新即可。

> **忘了密码**：直接重设环境变量即可 ——
> ```bash
> npx wrangler secret put ADMIN_PASSWORD
> ```
> 或去 Dashboard 的 Variables and Secrets 改。设完立即生效，不需要重新部署。

### 5. 加监控站点

后台「站点 → ＋添加站点」，填名称和地址即可。分类从下拉里选（只能选已有分类，
新建/改名/删除统一在左侧「分类」栏操作）。
**探测位置由「设置 → 探测」统一配置**，站点上不再有后端选项。

站点级字段里只有 **标识 / 显示名称 / 监控地址** 是必填，其余留空都有可用默认：

| 字段 | 默认 | 说明 |
|---|---|---|
| 标识 | — | 站点主键，而且**进 URL**（`/monitor?id=<标识>`）—— 改了它，已分享出去的链接就失效。只允许 `字母 数字 . _ -`（1–64 字符）：因为要进 query，用的是白名单字符集，前端 `pattern` 与后端校验**逐字符一致** |
| URL 显示 | 显示 | 选「隐藏」后，`/api/overview` 与 `/api/site` **都不再下发 url**（不是"下发了但前端不渲染"），前台也不渲染跳转按钮 —— 适用于 API 端点、内部系统这类"可用率可以公开、地址不想外传"的站点 |
| 期望状态码 | 空 | 空 = 接受 200–399（探测**不跟随重定向**，所以"站点在跳转"这件事本身看得见） |
| 连续失败几次判故障 | 3 | 一个字段驱动**三处**且口径完全一致：状态 badge 的红/黄分界、详情页「故障记录」、30 天色条的红/黄分界。未达阈值的失败是**黄「疑似故障（确认中 n/3）」**，达到阈值才是红。⚠️ 阈值按**次数**计，所以「多久才转红」≈ 阈值 × 监测间隔 —— 60 分钟间隔 + 阈值 3 就是 3 小时，这类站点建议把阈值设成 1 或 2 |
| 监测间隔 | 5 分钟 | 每隔多久探测一次 |
| 启用 | 启用 | 暂停后不参与调度 |

## 配置：都在这里改

**运行参数全部在后台「设置」里改，改完即时生效，不需要重新部署。**
`wrangler.toml` 里没有任何 `[vars]`（只有 `keep_vars = true` 与 D1 / 静态资源绑定）。

优先级：**后台设置（存 D1）> 环境变量 / secret > 代码内置默认**

| 分组 | 设置项 | 默认 | 说明 |
|---|---|---|---|
| 外观 | 站点标题 | 站点状态 | 前台标题与页头品牌名 |
| | 前台默认主题 | 跟随系统 | 跟随系统 / 浅色 / 深色（用户手动切换优先） |
| | 展示时区 · UTC 偏移 | 480 分钟 | 即 UTC+8。决定 30 天色条「一天」从哪一刻起算，服务端口径一致 |
| 探测 | Globalping Token | 空 | 空 = 匿名档 250 次/小时；配置后 500 次/小时 |
| | 探测位置筛选 | CN+datacenter-network | **全局**。下拉：中国 · 云机房 / 中国 · **全部网络**（`CN`，云机房 + 家宽）/ 中国 · 家庭宽带 / 东亚 / 西欧 / 北美，或选「自定义…」填任意 magic |
| | 每次探测点数 | 3 | 三档下拉：`1` 单点采样 / `3` 多探针兜底（默认）/ `5` 更稳；⚠️ 额度按点数计费，`cost = 点数` |
| | 探针超时 | 15 秒 | 整数秒 5–30，这是"告知远端探针最多跑多久"，不是"我们等多久" |
| | 证书降级阈值 | 14 天 | 剩余 ≤ 该值判为「降级」；0 = 只在证书已过期时降级 |
| | 响应偏慢阈值 | 2000 毫秒 | 最近一次响应超过该值判为「降级」；0 = 关闭该项判定 |
| 高级 | IP 版本 | 4 | 4 / 6（非法值按 4 处理 —— 它也是**环境变量**可设的项，写错不该让所有站点一起 422） |
| | 单次子请求预算 | 30 | 每轮出网子请求上限（1–35），**收取与发起都算在内**。免费层硬上限 50，而 D1 往返另计约 15–20 次，所以别贴着 50 设。额度用尽的站点会被**跳过**（记进 cron 日志的 `skipped`），而不是把整轮打成失败 |
| | 明细保留天数 | 30 | 过期记录由 cron 每天自动清理；**同时是色条天数上限** —— 保留 10 天时 `?days=90` 只返回 10 格，不会画出一排永远空着的格子 |
| | 最近检查条数 | 20 | 详情页「最近检查」最多列几条（5–200） |
| | 故障记录条数 | 10 | 详情页「故障记录」最多列几条（1–100） |

> **为什么位置是全局而不是每站点一份**：所有站点都走同一条 Globalping 链路，
> 每站点各存一份位置只会产生"N 份配置、实际只有一份生效"的错觉。

> **为什么默认采 3 个探针**：
> Globalping 把测量派给哪台探针由平台决定，且**不保证粘性** —— 实测同一
> `CN+Shanghai` 连测 4 次，落到 4 台不同探针（AS24364 / AS9929 / AS9808 / AS4812），
> 延迟 **477 / 66 / 93 / 48 ms**，相差近 10 倍。
> 单点采样时，那台机器所在链路的一次抖动会被 100% 记成「站点失败」，实测中国家宽
> 筛选下的单点失败率约 25%。
> 判定规则：
> - **一台成功即视为可达**：只有全部探针都失败才判故障。站点真挂时 3 台会同时失败，
>   检出能力不受影响；而「2 台同时抖动」这类假故障不会被误报
> - 全失败时要求**至少 2 张有效票** —— 本来派了多台却因平台故障只剩 1 台且失败，
>   可能只是它自己的链路问题，整次作废、不写记录。
>   ⚠️ 但「探测点数」设成 **1** 时没有这条保护：1 票就是选定的采样方式，失败如实入账
>   （否则该配置下每轮都作废，站点挂了也不会变红）
> - `failureSource = internal`（Globalping 平台自身故障）**不计票**，与「没拿到数据」区分开
> - 代表值取**成功票内的中位数**，不取最快 —— 取最快会让页面长期显得比实际更快
>
> 关于「为什么不用多数表决」：单点失败率 25% 时，3 台里「≥2 台失败」的概率是
> `3×0.25²×0.75 + 0.25³ ≈ 15.6%`，配上连续 3 次仍有约**每天 1 次**误报；
> 而「全灭」的概率只有 `0.25³ ≈ 1.56%`，低一个数量级。
> 对照：UptimeRobot 单区域模式同样是「主引擎 + 2 个远程地点全失败才 Down」；
> Better Stack 用 3/4（75%）是因为它的探针在优质机房、单点失败率远低于 25%，
> 直接套用到国内链路上会天天误报。
>
> 代价是额度按点数计费（`cost = 点数`）：5 分钟间隔的站点是 12 次/小时，
> 免费额度 250/小时下约可支撑 20 个站点，配 token（500/小时）翻倍；
> 1 分钟间隔则只有 4 / 8 个。具体上限见「容量」一节的三道卡口。
> 档位由后台下拉的 `<option>` 定义（当前 **1 / 3 / 5**），选定即原样生效 ——
> 服务端**刻意不做校验**（要加档位只加一行 `<option>` 即可）。

### 敏感值（都用环境变量）

| 名称 | 说明 |
|---|---|
| `ADMIN_PASSWORD` | **必设**。后台唯一的登录凭据；**不设则后台整体停用**（`/admin` 只显示设置指引，后台接口一律 403） |
| `GLOBALPING_TOKEN` | 可选。Globalping 额度 250 → 500 次/小时（也能在后台「设置 → 探测」里填，存 D1） |

```bash
npx wrangler secret put ADMIN_PASSWORD
npx wrangler secret put GLOBALPING_TOKEN
```

用 GitHub 自动部署时，改在 Dashboard：**项目 → Settings → Variables and Secrets**（类型选 Secret）。

> `ADMIN_SECRET` 用于固定会话签名密钥（不设也行，会在 D1 里自动生成随机值）。

## 接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/health` | 公开 | **部署自检**：D1 绑定是否生效、8 张表缺哪张、密码配没配、本次是否自动补了结构，外加 `probe`（Globalping 最近一次成功/失败/429 退避窗口）。排障先看这个 |
| GET | `/api/overview` | 公开 | 统计 + 分组 + 30 天色条 + SSL，边缘缓存 300s（`config_version` 变更即换 key）。「可用率」口径是**滚动 24 小时**，与详情页趋势图同一个窗口、同一批行；已暂停站点不计入分母。站点勾了「隐藏 URL」时，该条目的 `url` 为 `null` |

| GET | `/api/admin` | 登录 | 站点 + 状态 + 分类 + 证书 + 设置 + `probe`（探针健康，**一次拿全**） |
| POST | `/api/login` `/api/logout` | 公开 | |
| GET/POST | `/api/settings` | 登录 | |
| GET/POST/DELETE | `/api/categories` | 登录 | |
| POST/DELETE | `/api/sites` | 登录 | 写入 / 删除 |
| POST | `/api/run`、`/api/test` | 登录 | 调试：手动跑一轮 / 测单个站点 |

Token 类设置**只写不读**——读取接口只返回掩码（`glp_****ghij`）和是否存在。

## 排障

部署后页面报错，**先打开 `/api/health`**（不需要登录，库没建好时也能访问）：

```bash
curl -s https://<你的域名>/api/health?pretty=1
```

健康时返回 `ok: true` 与 8 张表名；不健康时 `ok: false` 并有 `hint` 说明下一步。

`/api/health` 同时也是**自愈入口**：它在读取状态之前会先让库结构就位，
所以库是空的时候打开它，表会被直接建好。返回里 `schema.auto_applied` 会说明这次做了什么：

| `schema.auto_applied` | 含义 |
|---|---|
| `none` | 结构本来就是最新的（绝大多数时候） |
| `created` | 这个库原本一张表都没有，本次建好了（`from_version: -1`） |
| `repaired` | 库已存在但缺表/结构旧，本次补齐了（`from_version` 是补之前的版本） |
| `failed` | 自动补结构失败，原因见 `schema.error` |

典型返回与处理：

| 返回 | 含义 | 处理 |
|---|---|---|
| `db_bound: false` | `env.DB` 不存在，D1 绑定没生效 | `npm run setup`（建库并把 `database_id` 写回 `wrangler.toml`）；然后重新部署 |
| `missing_tables: [...]` 非空 | 库连通但表建不出来 | 看 `schema.error`：常见是 D1 写额度耗尽或库被删 |
| `ok: true` 但 `password_set: false` | 部署完整，只是没设密码 | `npx wrangler secret put ADMIN_PASSWORD`（**类型要选 Secret**） |

> 表结构与代码不一致（`no such column`）不在自愈范围内 —— 自动建表只会**建缺的表**，
> 不会改已有的表。这类问题看 [改表结构](#改表结构)。

> 所有 5xx 现在都会返回 JSON（`{ok:false, error, hint?}`），不会再出现
> 「空格 500」——异常逃出 Worker 时浏览器只显示 `Failed to load resource: 500 ()`，
> 前端拿不到任何文案，那是最难排查的一种失败态。

## 结构

```
src/
  index.js      路由（鉴权、接口、cron 调度）
  db.js         数据层：所有 SQL 集中在此 + 库结构自举（ensureSchema）
  schema.js     ⚠️ 生成物：schema.sql 转出的建表语句数组，不要手改
  migrations.js 增量迁移：给已有的旧库补列（新库用不到）
  probe.js      Globalping 发起 / 收取 / 判定（含证书提取）
  origin.js     「探测来源」标签的唯一拼装处（GP:CN · Beijing/9808）
  settings.js   运行参数元信息：唯一默认值来源 + 合法值校验
  auth.js       常量时间比较 + HMAC 签名会话（密码只比环境变量，不存哈希）
public/
  index.html / app.js        前台总览
  monitor.html / monitor.js  站点详情（图表为原生 SVG，无图表库）
  admin.html / admin.js      后台
  app.css                    样式
scripts/
  setup-d1.mjs   自动准备 D1：建库 + 写绑定 + 建表（幂等）；目标 production / local
  gen-schema.mjs schema.sql → src/schema.js（`--check` 只校验不写）
schema.sql        建表语句的**唯一真源**（全部 IF NOT EXISTS，可重复执行）
wrangler.toml     只有绑定配置（D1 / 静态资源），**不含域名**；运行参数一律在后台「设置」里改
```

数据表：`sites` `checks` `state` `pending` `ssl` `checks_daily` `categories` `meta`
索引：`checks` 上两个 —— `(site, ts DESC)` 供详情页取某站一段，
`(ts DESC, site, ok)` 供清理过期行（`DELETE ... WHERE ts < ?`）按时间范围定位，
不用再为「近 24h 跨站聚合」服务 —— 那个聚合已经从扫明细改成读 `checks_daily` 了

`checks_daily` 是按天物化的汇总（每站每天 1 行：次数、成功数、当天最长连续失败段），
是 30 天色条和按天统计的**唯一数据源**。它把「读 30 天色条」的代价从每站 4 万行
降到 30 行，见下面的「容量」一节。

## 容量：能监测多少个站点

D1 免费计划每天 **500 万行读 / 10 万行写**（按 UTC 0 点重置，即北京时间早 8 点）。
超限不是计费，而是**整库拒绝查询** —— 监控与后台一起挂。所以下面的数字要留余量。

以下是实测值（本地 workerd + SQLite，按 1 分钟间隔、单站 30 天数据逐条累加 `meta`），
不是估算：

**写**：一次检查 = 8 行（`pending` 2 + `checks` 3 + 删 `pending` 1 + `state` 1 + `checks_daily` 1），
证书 6 小时内只写一次，不计入日常。

| 间隔 | 每站每天 | 10 万行能撑 |
|---|---|---|
| 1 分钟 | 12,960 | **7 站** |
| 5 分钟 | 2,592 | 38 站 |
| 10 分钟 | 1,296 | 77 站 |

公式：**站点上限 ≈ 7.7 × 间隔分钟数**。

**读**：`/api/overview` 回源 ≈ 站点行 + 30 天色条行（`31 × N`）+ **24h 明细行数**。
最后一项是"每站 24 小时可用率"的代价，但它有天然上界：每天总检查数被 Globalping
额度封在 **2,000 条（匿名）/ 4,000 条（Token）**，所以无论站点怎么配，单次回源
最多几千行。按 300s 缓存算，单机房每天回源 288 次 → **57 万 / 115 万行，占日额度 12% / 23%**。

`/api/site` 回源 = 该站在 24h 窗口内的明细行数（= 1,440 / 间隔分钟数），
序列、可用率、故障记录 `LAG` 共用这一个窗口（各扫一遍，所以是 3 倍）。
1 分钟粒度 = 4,320 行/次，5 分钟 = 864 行/次；详情页本来就是点进去才看，量级可忽略。

**另外两道卡口**（与 D1 无关，但会先撞上）：

| 限制 | 1 分钟间隔的上限 |
|---|---|
| Globalping 500 次/小时（注册用户；未注册 250） | 8 站（未注册 4 站） |
| 子请求预算 30/分钟 ÷ 每站 2 次 | 15 站 |

三者的最小值就是真实上限。1 分钟间隔下是 **7 站**，瓶颈在 D1 写入。

> 想知道自己用了多少：Cloudflare 控制台 → Workers & Pages → D1 → 选中库 →
> Metrics → Row Metrics。出现 `daily limits exceeded` 就是超了。

## 库结构自举（为什么建表不靠命令）

**Worker 在第一次请求时自己检查库结构，缺表就按 `schema.sql` 建好。**
不需要任何人先跑 `npm run deploy`。

### 为什么必须这样

建表原先只发生在 `npm run deploy` 里的 `scripts/setup-d1.mjs`。问题在于
**部署路径有好几条，只有一条会执行那个脚本**：

| 部署方式 | 会不会跑 setup-d1.mjs | 旧行为 |
|---|---|---|
| 本地 `npm run deploy` | ✅ | 正常 |
| 控制台连 GitHub 自动构建，Deploy command 填 `npm run deploy` | ✅ | 正常 |
| 同上，但填的是 `npx wrangler deploy` | ❌ | **部署成功、接口全报 `no such table: meta`** |
| CI / 脚本里直接 `wrangler deploy` | ❌ | 同上 |
| Dashboard 里直接改代码 | ❌ | 同上 |

失败时的现象很误导人：Worker 部署成功、静态页面能打开，但每个接口都是
`500`，日志里只有一句 `no such table: meta` —— 而「怎么建表」这件事
在界面上没有任何入口。

### 怎么做的

```
请求进来
  → ensureSchema(env)
      读 meta.schema_v
        · 已是最新版本  → 直接返回（每个 isolate 只多 1 次单行读）
        · 版本更旧/没有 → 跑 schema.js 里的全部 CREATE ... IF NOT EXISTS
                        → 跑 migrations.js 里「比库里版本新」的那些 ALTER
                        → 把版本号写回 meta
  → 之后才是设置加载与认证闸门
```

三个关键点：

- **幂等**：所有建表语句都是 `IF NOT EXISTS`；迁移里重复补列的错误被识别并吞掉。
- **只跑一次**：缓存按 **D1 绑定对象**记（`WeakMap`），同一库只查一次版本号；
  并发请求共享同一个 Promise，不会并发建表。
- **失败不缓存**：D1 抖动、额度暂时耗尽这类问题下一刻可能就好了，
  缓存住失败会让这个 isolate 的余生都返回同一个错误。

### 代价

| 项 | 量 |
|---|---|
| 正常状态下每个 isolate 生命周期 | **多 1 次 D1 读**（最多 1 行） |
| 库为空/结构旧时 | 一次性的 10 条 DDL + 1 条版本写入，之后不再发生 |
| Worker CPU | 不变 —— DDL 在 D1 侧执行，等 I/O 不计入那 10ms 上限 |

### 一个坑：`schema.sql` 要变成 JS 才进得了包

Worker 的包由 wrangler 打包，**运行期没有文件系统**，读不到 `schema.sql`。
想让代码直接用那份 SQL，直觉是配 Wrangler 的 module rule 把它当文本导入：

```toml
[[rules]]
type = "Text"
globs = ["**/*.sql"]
```

**实测这条路走不通**：构建不报错，但产物里反而多出一个独立的 `schema.sql` 文件，
`import` 进来的是 `undefined` —— 静默失败，比报错更难发现。

所以改成生成：`scripts/gen-schema.mjs` 把 `schema.sql` 解析成语句数组写进
`src/schema.js`（生成物，提交进仓库）。`schema.sql` 仍是唯一真源，
`npm run deploy` / `npm run dev` 会自动重新生成；`npm run check:schema`
用来确认两边没漂移。

> 生成物要提交，是因为云平台上直接 `wrangler deploy` 时**只会用仓库里的文件**，
> 不会跑生成脚本。这也是为什么改完 `schema.sql` 必须 `npm run schema` 再提交。

## 改表结构

`schema.sql` 里的建表语句全是 `IF NOT EXISTS`，对「表已存在但少一列」**什么都不做**。
所以加字段要走迁移，不能只改 `schema.sql`（那只对新建的库有效）：

1. 改 `schema.sql`，把顶部的 `-- schema-version:` 加 1
2. 在 `src/migrations.js` 里追加一条（v2 = `checks_daily` 建立，v3 = `state.void_streak`，
   下一个可用版本号是 **v4**）：

   ```js
   export const MIGRATIONS = [
     { v: 4, stmts: ["ALTER TABLE sites ADD COLUMN note TEXT"] },
   ];
   ```

3. `npm run schema` 重新生成 `src/schema.js`，连同上面两处一起提交

之后：**新库**直接按完整定义建表，跳过迁移；**旧库**先补缺失的表/索引，
再跑「比库里版本新」的迁移，然后写回新版本号。不重建库、不丢数据。

需要**搬数据**的迁移（比如 v2 把明细汇总成 `checks_daily`）不写在 `MIGRATIONS` 里 ——
静态语句没法判断库有多大，写进 `db.js` 才能先量行数、超限就跳过，
避免一次回填把当天读额度用光。v2 的回填上限是 10 万行明细，结果在 `/api/health`
的 `schema.backfill` 里（`done: false` 表示因规模跳过，历史色条会是空的）。

三条约束：

- 迁移语句必须幂等。重复补列会报 `duplicate column name`，这一条被吞掉；
  其它错误照常抛出，不会伪装成成功。
- 只写 `ADD COLUMN` 这类安全操作。SQLite 删列/改类型要重建整张表，
  不适合在请求路径上自动做 —— 那种变更应当人工处理。
- 加 `NOT NULL` 列时必须同时给 `DEFAULT`，否则已有行没法填充。

## 几点设计取舍

- **探测为什么分两阶段**：Workers 免费计划每次调用最多 50 个子请求，轮询等结果会吃光额度。
  Globalping 改为「本轮发起、下轮收取」，每站点压到 **2 个子请求**（1 次创建 + 1 次取结果）。
- **为什么提前一个 cron 周期发起**：调度器每分钟醒一次，而两阶段的探测本身就跨一个 cron
  周期。若等「距上次**结果**满 interval」才发起，结果落地会比设定值晚一整轮 ——
  1 分钟的间隔实际变成 2 分钟。所以按 `interval − 1 个 cron 周期` 提前发起，
  让**结果**落在间隔上。判定到期时另留 15 秒宽容量 —— 否则「间隔 = 1 分钟」会因差 0.7 秒
  被判成未到期，白等一整分钟。
- **证书为什么不再单独检测**：Globalping 的 HTTP 测量结果里本来就带 `result.tls`
  （`authorized` / `issuer` / `subject` / `expiresAt` / `protocol`），随探测顺带写入即可。
  旧实现为证书另发一轮测量、单站最坏 14 个子请求、25 秒窗口轮询，**纯属浪费额度**。
- **剩余天数为什么不落库**：相对时间写进库那一刻就开始过期。读侧一律用
  `julianday(expires_at) - julianday('now')` 现算 —— 否则「今天到期」的证书
  要等第二天复核跑完才变红，中间 24 小时页面一直显示"剩余 1 天"。
- **为什么用反范式的 `state` 表**：首页要「每个站点的最后一条结果」。用窗口函数
  （`ROW_NUMBER() OVER (PARTITION BY site ORDER BY ts DESC)`）等于对 `checks` 全表分区排序，
  代价随历史增长；而落库时顺手把快照写进 `state`，读侧就只是主键 LEFT JOIN。
- **后台为什么要聚合接口**：实测从国内访问 CF 边缘，单个请求 TTFB 中位约 780ms（静态文件、
  走缓存、不进 Worker 也是这个数）——瓶颈在链路，不在数据库。所以优化方向是**减少请求数**，
  后台从串行 3 个请求合并成 1 个 `/api/admin`。
- **密码为什么不做成后台可改**：那样就得在 D1 存哈希、还要处理「改密码如何作废旧会话」。
  密码本质是部署期配置，放环境变量更简单、更容易审计，也省掉一类状态。
- **登录限速在 D1 上计数，且按来源 IP 分桶**：低流量下 Workers 经常每次请求都新建 isolate，
  内存 Map 形同虚设。计数键是 `CF-Connecting-IP` 的 SHA-256 前 16 位（不落明文地址），
  整个映射存在 `meta.login_fail` 一列里（`{ "<hash>": [ts,...] }`，只留最近 60 秒内有记录、
  最多 64 个来源）。
  - 为什么不全局计数：全局锁 = 任何人发 8 次错误密码就能把管理员**永久**挡在门外，
    成本几乎为零。按 IP 分桶后，被锁的只有攻击者自己，管理员换网络照样能进。
  - 60 秒滑动窗口，不是"永久封禁"：真正需要长期防护时应该上 Cloudflare Access，
    而不是在应用层做永久黑名单。
- **域名为什么不写进 `wrangler.toml`**：`routes` 是声明式的，一旦写进来，每次部署都会按配置
  重建 DNS 与证书；而控制台手动加的域名是独立持有的路由资源，不在配置里就不会被 wrangler 动。
  交给人工绑定后，换域名不必改仓库、也不必重新部署。
- **所有非 GET 请求为什么要校验同源**：Cookie 是 `SameSite=Lax`，它挡不住"会改状态的 GET 导航"。
  与其依赖"每个写接口都记得写成 POST"，不如统一加一道校验（`Origin` → `Sec-Fetch-Site` → 拒绝）。
- **黄色（降级）为什么表示「确认中」而不表示「部分探针失败」**：
  主流工具里黄色都是「失败但还没被确认」——Uptime-Kuma 的 `PENDING` 就是重试期间的状态，
  重试用尽才转 `DOWN`。这里对齐这个语义：连续失败 1..n-1 次是黄（`疑似故障（确认中 2/3）`），
  达到阈值才红。这样状态 badge 与 30 天色条、「故障记录」**共用同一个阈值**，
  不会出现「圆点红了但色条没红」。
  而「部分探针失败」刻意不上色：单点失败率 25% 时，3 台里至少 1 台失败的概率是
  `1 − 0.75³ ≈ 57.8%` —— 一半以上的时间都会是黄的，颜色就失去信息量了。
  那个信号留在详情页的票型标注上（`City/ASN (1/3)`），只在出现分歧时写。
- **「探针连续 N 轮无结论」为什么会变黄**：拿不到结论（探针全灭 / 平台内部故障 /
  收取失败 / 429 退避）时，我们**不写任何检查记录** —— 把"没测到"写成"故障"是编造数据。
  但那会让页面永远停在上一次的"正常"，只是「X 分钟前」越变越大，监控静默失效。
  所以单独记一条 `state.void_streak`：每轮无结论 +1、拿到结论清零，连续 3 轮就把站点
  降级为「探针连续 N 轮无结论」。要分清"站点好了"和"我们瞎了"，这是唯一可靠的办法。
  根因在 `/api/health` 的 `probe` 与后台设置面板的探针状态行（最近成功 / 最近错误 / 429 退避）。
- **「最近检查」里看到故障、「故障记录」却是空的**——这不是 bug，是两处口径不同：
  - 「最近检查」是**原始明细**，每一次失败都会列出来（红标「故障」）。
  - 「故障记录」是**故障事件**，把连续失败合并成一段，且只记「连续失败次数 ≥ 该站点阈值」
    的段（阈值 = 站点表单里的「连续失败几次判故障」，默认 3）。单次抖动（下一拍就恢复）
    刻意不记，否则每次网络波动都会刷出一条事件。
  - 另外故障记录只统计**当前窗口内的段** —— 窗口与趋势图同源（最近 24 小时；
    新站点则从首条记录算起），所以卡片标题永远和图表说同一件事。
    变化点查询要逐行看 `LAG(ok)`，窗口封顶 24 小时就是为了让这个扫描有上界。
  - 段内失败次数由时长估算：`段时长 ÷ 间隔`。`start` 是首个失败点、`end` 是其后第一个成功点，
    所以段时长恰好 = 失败次数 × 间隔 —— **不要再 +1**：那会把「1 次失败」估成 2 次，
    使阈值判定整体少一次，连单次抖动都会被当成故障事件。
- **30 天色条的颜色跟「故障记录」同一口径**（绿 = 全天正常、黄 = 当天只有零星抖动、
  红 = 当天出现过真故障）。
  - 数据来自 `checks_daily`，写入时逐次累加：次数 +1、成功数 +ok、
  当天最长连续失败段取最大值。跨过日界则连续数从头记（宁可少标红）。
  - 「连续」用的是 `state.consecutive_fail` 同一个计数 —— 与首页圆点、故障记录
  **同一个定义**，不会再出现「圆点红了、色条还是黄」。
  - 读色条只读 30×N 行，不再是每站 4 万行的聚合扫描（见「容量」一节）。
- **删除站点是级联删除**：`sites` / `checks` / `checks_daily` / `ssl` / `state` / `pending` 一次 batch 全清，
  **不可撤销**（列表底部与删除确认框都写明了）。留着历史明细看起来更"安全"，实际会污染
  首页统计 —— 分子分母还含着已删站点，而「监控总数」已经不含它了。
- **读路径尽量少一次 D1 往返**：`loadSettings()` 一开始就把整张 `meta` 读进内存，
  所以配置版本号（缓存 key 的一部分）、会话密钥、登录失败计数都从内存取，
  不再各发一条 `SELECT ... FROM meta WHERE key = ?`。
- **cron 日志一眼能看懂**：`due`（本轮该查几个）/ `collected`（收回并落库几条）/
  `gpDropped`（丢弃且未落库的 pending，正常恒为 `[]`）/ `skipped`（额度不够被跳过的站点）/
  `subreqUsed` vs `subreqBudget`（出网子请求用量）/ `ssl`（顺带更新的证书数）/
  `cleaned`（清理的过期明细）/ `orphans`（清理的孤儿行）/ `errors`（分段失败列表）。
  **`errors` 非空但其它字段正常**是设计如此：每段独立 try/catch，一段失败不中断整轮。

## 本地开发

```bash
npm install     # 装 wrangler（唯一 devDependency）
npm run dev
```

默认 `http://localhost:8787`。`npm run dev` 会先在本机的 D1 副本上建表再启动，直接可用。

> **本地也要管理员密码**：鉴权是 fail-closed，不给本地留特例 —— 否则很容易变成
> "本地能进后台、部署上去进不去"这种最难查的不一致。项目里有一份 `.dev.vars`
> （已被 `.gitignore` 排除）写了 `ADMIN_PASSWORD=dev`，本地登录就用 `dev`；
> 想换别的值改这个文件即可，改完重启 `npm run dev`。

> `npm install` 建议不要跳过：`scripts/setup-d1.mjs` 优先用本地的 wrangler，
> 只有本地没装时才退回 `npx`，而 npx 缓存损坏过（缺 `ws` 模块）。

### 命令一览

| 命令 | 作用 |
|---|---|
| `npm run dev` | 本地起服务（先给本机 D1 副本建表） |
| `npm run deploy` | 准备生产库 + 部署 |
| `npm run setup` | 只准备数据库，不部署 |
| `npm run schema` | 改完 `schema.sql` 后重新生成 `src/schema.js` |
| `npm run check:schema` | 校验 `src/schema.js` 与 `schema.sql` 是否同步（CI 可用） |

> `dev` / `setup` / `deploy` 都会自动先跑 `npm run schema`，正常流程里不用单独执行。

其它常用：

```bash
npx wrangler secret put ADMIN_PASSWORD      # 设/改管理员密码
npx wrangler d1 execute uptime-db --remote --command "SELECT COUNT(*) FROM sites"
npx wrangler tail                            # 看实时日志
```
