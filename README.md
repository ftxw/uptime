# uptime

站点可用性监控。**Cloudflare Workers + D1 + Durable Object**，零 npm 依赖、零构建步骤，
`npx wrangler deploy` 直接上线。

- 前台：总览页（分组 + 30 天色条 + 证书剩余天数）、单站点详情页（延迟趋势、故障记录）
- 后台：左右两栏管理（左分类、右站点），分类与站点都可拖拽排序，需管理员密码登录
- 三探测后端：Cloudflare Durable Object（区域可控）/ Globalping（真实网络视角）/ 大陆探测臂（`cn`）
  —— `cn` 的出口在中国大陆机房，测国内站点得到的是**真实的境内视角**。CF 在大陆没有可落地的
  计算节点，所有 CF 探测本质是「境外打境内」，跨境链路抖动会淹没真实延迟 —— 这是它存在的唯一理由

## 部署

D1 数据库的**创建、绑定、建表都由 `scripts/setup-d1.mjs` 自动完成**——
不需要手工 `d1 create`、不需要复制 `database_id`、不需要单独跑建表。
脚本是幂等的：库已存在就复用，多次执行不会产生副作用。

**域名不由脚本绑定**，你在 Cloudflare 控制台自己绑（见第 1 步）。这样换域名不必改仓库、
也不必重新部署。

需要你自己做的只有两件事：**绑域名**、**设管理员密码**。

### 1. 授权 + 绑定域名

```bash
npx wrangler login          # 首次需授权 Cloudflare 账号
```

`wrangler.toml` 里**刻意不写 `[[routes]]`**：域名不跟着配置走，避免每次部署都用配置去
覆写 DNS 与证书。绑定一次性敲定后长期有效：

> **Workers & Pages → 选中本项目 Worker → Settings → Domains & Routes → Add → Custom domain**

> 同理，预览环境的域名也在这个界面的 `uptime-preview` Worker 上绑。
>
> ⚠️ 不要只依赖 `workers.dev` 域名 —— 实测在中国大陆不可达。
> 之所以保留了 `workers_dev = true`：绑域名之前总得有个能自检的地址。

### 2. 设置管理员密码

密码**只来自环境变量** `ADMIN_PASSWORD`，后台没有改密码的入口（改密码 = 改这里）。

**必须在部署前设好** —— 鉴权是 fail-closed：没配这变量时后台**整体停用**
（打开 `/admin` 只会看到「后台已停用」的说明页，所有后台接口一律 403）：

```bash
npx wrangler secret put ADMIN_PASSWORD
```

用 GitHub 自动部署（Workers Builds）的话在 Dashboard 配一次：

> **Workers & Pages → 选中本项目 → Settings → Variables and Secrets → 添加**
> 名称填 `ADMIN_PASSWORD`，**类型必须选 Secret**（不是 Text），保存。
> 之后每次部署都会自动注入，无需重复配置。

> ### ⚠️ 为什么必须选 Secret —— 实测踩过的坑
> `wrangler deploy` 会把「版本的全部明文变量」按本地配置重写，所以
> **只在控制台填的明文（Text）变量，会在下一次部署时被整个清掉**
> （以 `wrangler.toml` 为准，`[vars]` 里没有的就视为"已删除"）。
>
> 症状很有迷惑性：变量明明填了，但 Worker 运行时读不到，打开 `/admin` 只会看到
> 「后台已停用 · 未设置管理员密码」——看起来像代码 bug，其实是变量被部署清空了。
> （fail-closed 的好处就在这里：配置丢了是"用不了"，而不是"谁都能用"。）
>
> | 类型 | 设置方式 | 重部署后是否保留 |
> |---|---|---|
> | Secret | 控制台或 `wrangler secret put` | ✅ 永远保留 |
> | 明文 Variables | 仅控制台填 | ❌ 会被清掉 |
> | 明文 Variables | 写进 `wrangler.toml` 的 `[vars]` | ✅ 随部署生效 |
>
> 本项目已在 `wrangler.toml` 里设了 **`keep_vars = true`**，让 wrangler 不去动
> 控制台上的变量；但**敏感值仍然推荐用 Secret**（值不会明文可见，也不进代码库）。

> **为什么不做成"没设密码就先开放后台"**：那样等于用一个 5 秒就消失的提示，
> 去兜住"任何人打开这个网址都能改配置、读到告警 Webhook 与 Globalping Token"这件事。
> 注意 `/admin` 这个 HTML 是静态资源，由 Assets 直接返回、根本不经过 Worker，
> 拦不住也没必要拦 —— 页面里只有空壳，数据一个字段也拿不到。
>
> **为什么不做成"首次打开时让你设一个密码"**：那个接口本身就没有鉴权，
> 谁先打开谁就能把密码设成自己的，反过来把主人锁在外面。
>
> **为什么不做成后台可改**：那样就得在 D1 里存密码哈希，还要额外处理「改密码如何
> 作废旧会话」。而密码本质是部署期配置，放环境变量更简单、也更容易审计。
> 改密码的代价就是重新设置一次变量，不需要重新部署。

### 3-A. 命令行部署（一条命令）

生产：

```bash
npm run deploy
```

预览（独立 Worker + 独立数据库，改坏也碰不到生产）：

```bash
npm run deploy:preview
```

两个命令做的事完全一样，只是目标不同：

1. 列出账号下的 D1，按目标找 `uptime-db`（预览是 `uptime-db-preview`）
2. **没有就创建**，并把 `database_name` 与 `database_id` **写回 `wrangler.toml`**（即自动绑定）；
   已有则校验配置与实际是否一致，不一致就修正
3. 执行 `schema.sql` 建表
4. **校验表结构与 `schema.sql` 一致**，不一致就中止部署

然后才执行 `wrangler deploy`。全过程幂等，反复跑不会重复建库。

> 第 4 步是必要的：`schema.sql` 全部是 `IF NOT EXISTS`，对「已存在但结构较旧」的表
> **不会补列**。没有这道校验的话，改过表结构后部署照样通过，直到运行时才报
> `no such column`。本项目不做增量迁移 —— 结构变了就换库名重建（见下方）。

> ⚠️ **`wrangler.toml` 里的 `database_id` 不要提交**：第 2 步写回去的是**本机账号的实际
> uuid**，只对当前账号有效。跑完 `setup` / `deploy` 后 `git status` 里 `wrangler.toml` 会
> 显示为已改动 —— 把它还原成空值 `""` 再提交（本仓库里它就是空的）。
> 脚本只认 `database_name`、不认已有 uuid，留空才能保证换账号/换环境时**自动对齐**；
> 一旦提交上去，就等于固化了一个只对某次部署有效的值，换环境必然指向不存在的库。

预览环境（`npm run deploy:preview`）与生产的差异，都是刻意的隔离：

| | 生产 | 预览 |
|---|---|---|
| Worker | `uptime` | `uptime-preview` |
| D1 | `uptime-db` | `uptime-db-preview`（**独立库**） |
| 定时任务 | 每分钟 | **不跑**（`crons = []`） |

> 预览**必须**有自己的库，否则预览上的任何写操作都会直接落到生产数据上，等于没隔离。
> 预览**必须**关掉 cron —— wrangler 的命名环境会继承顶层 `[triggers]`，不清空的话
> 两个 Worker 会每分钟各探测一遍，白白双倍消耗额度，还要多占一个 cron 名额
> （免费计划每账号上限 5 个）。
>
> 两个环境的域名同样都在控制台手动绑定，配置里不写 `[[routes]]`。

> 只想做数据库准备、不部署：`npm run setup` / `npm run setup:preview`
>
> 换库名：`D1_NAME=my-db npm run deploy`；换 D1 主区域：`D1_LOCATION=wnam npm run deploy`。

### 3-B. 连接 GitHub，推送即部署

在 Cloudflare Dashboard 操作（只需配一次）：

1. **Workers & Pages** → **Create** → 切到 **Import from Git** 标签
2. 授权 GitHub，选中本仓库（若没看到，点 *Configure GitHub app* 调整仓库可见范围）
3. 构建配置：

   | 项 | 值 |
   |---|---|
   | Framework preset | **None** |
   | Build command | 留空（本项目无构建步骤） |
   | **Deploy command** | **`npm run deploy`** |
   | Root directory | `/`（若本项目在仓库子目录里，填子目录名） |

4. 保存即触发首次部署；此后**每次 `git push` 到 `main` 都会自动部署**

> ⚠️ Deploy command 要填 `npm run deploy`，**不要**填 `npx wrangler deploy`——
> 前者会先跑 D1 准备脚本，后者会跳过，新环境上会因为没有 `database_id` 而失败。
>
> 生产分支默认 `main`。不同则在 Settings → Builds 改 *Production branch*。
> CI 环境由 Cloudflare 自动注入 `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID`，不需要配密钥。

### 4. 首次访问

访问 `https://<你的域名>/admin` 登录后台，密码就是第 2 步设的 `ADMIN_PASSWORD`
（30 天免登录，Cookie 为 `HttpOnly + SameSite=Lax + Secure`）。
没设过那个变量的话，这个页面只会显示「后台已停用」与设置步骤 —— 照上面的步骤补上再刷新即可。

> **忘了密码**：直接重设环境变量即可 ——
> ```bash
> npx wrangler secret put ADMIN_PASSWORD
> ```
> 或去 Dashboard 的 Variables and Secrets 改。设完立即生效，不需要重新部署。

### 5. 加监控站点

后台「站点 → ＋添加站点」，填名称和地址即可。分类从下拉里选（只能选已有分类，
新建/改名/删除统一在左侧「分类」栏操作）。
探测后端按站点选（`cf` / `globalping` / `cn`，**必选**），**位置则由「设置 → 探测」统一配置**。

站点级字段里只有 **标识 / 显示名称 / 监控地址** 是必填，其余留空都有可用默认：

| 字段 | 默认 | 说明 |
|---|---|---|
| 标识 | — | 站点主键，而且**进 URL**（`/monitor?id=<标识>`）—— 改了它，已分享出去的链接就失效。只允许 `字母 数字 . _ -`（1–64 字符）：因为要进 query，用的是白名单字符集，前端 `pattern` 与后端校验**逐字符一致** |
| URL 显示 | 显示 | 选「隐藏」后，`/api/overview` 与 `/api/site` **都不再下发 url**（不是"下发了但前端不渲染"），前台也不渲染跳转按钮 —— 适用于 API 端点、内部系统这类"可用率可以公开、地址不想外传"的站点 |
| 期望状态码 | 空 | 空 = 接受 200–399（探测**不跟随重定向**，所以"站点在跳转"这件事本身看得见） |
| 正文关键字 | 空 | 空 = 不校验。⚠️ 只对 `cf` / `cn` 后端有效 —— Globalping 的 HTTP 测量**不返回响应正文**，对 GP 站点此项会被忽略（后端不落库并回一条 warning 提示）。`cn` 探测臂会读正文，此项**真实生效** |
| 连续失败几次告警 | 3 | 一个字段驱动三处：告警推送、详情页「故障记录」、30 天色条的红/黄分界。⚠️ 推送是**边沿触发**：达到阈值时推一次「故障」、恢复时推一次「恢复」，故障持续期间不会重复推。判定依据是独立的 `state.alerted` 标志，**不是**"计数恰好等于阈值" —— 后者在故障期间把阈值调小就永远不再触发 |
| 监测间隔 | 5 分钟 | 每隔多久探测一次 |
| 启用 | 启用 | 暂停后不参与调度 |

### 6. 启用大陆探测臂（可选）

`cn` 后端**不是开箱即用**的 —— 它依赖一个**独立部署在中国大陆**的探测臂（见顶层目录 `cn-probe/`）。
要用它，二选一：

- 后台「设置 → 探测 → 大陆探测臂端点」填端点（推荐，改完即时生效，不必重新部署）；
- 或配环境变量 `CN_PROBES`（逗号分隔，可多个 → **多端点做多数表决**）。令牌配 `CN_TOKEN`，
  超时可调 `cn_timeout_ms`。

**不填端点时，配了 `cn` 的站点会自动降级到 CF 边缘探测**（来源标记为 `CF:…（降级）`）——
不会因为没有探测臂就停摆。

⚠️ **端点有两种形态**，代码都支持，但长期只用前者：

| 形态 | 形如 | 说明 |
|---|---|---|
| 裸域名（正式） | `https://probe.example.com` | 绑了自定义域名，直接请求即可、无需 cookie。**长期用这个** |
| EdgeOne Makers 预览链接 | `https://xxx.edgeone.cool?eo_token=…&eo_time=…` | 带访问鉴权的预览地址：直接请求会 401。代码会**先 GET 一次换出 `Set-Cookie`，再带 cookie 请求去掉 query 的干净 URL**（`eo_token` 3 小时有效，命中后会缓存 2.5h 少打一次）。⚠️ `eo_token` **每 3 小时失效、且每次部署轮换** —— 只适合验证链路，**不要用于长期生产** |

## 配置：都在这里改

**运行参数全部在后台「设置」里改，改完即时生效，不需要重新部署。**
`wrangler.toml` 里没有任何 `[vars]`（只有 `keep_vars = true` 与 D1 / Durable Object 等绑定）。

优先级：**后台设置（存 D1）> 环境变量 / secret > 代码内置默认**

| 分组 | 设置项 | 默认 | 说明 |
|---|---|---|---|
| 外观 | 站点标题 | 站点状态 | 前台标题与页头品牌名 |
| | 前台默认主题 | 跟随系统 | 跟随系统 / 浅色 / 深色（用户手动切换优先） |
| | 展示时区 · UTC 偏移 | 480 分钟 | 即 UTC+8。决定 30 天色条「一天」从哪一刻起算，服务端口径一致 |
| 探测 | CF 区域组 | apac | **全局**。`apac`香港、`apac-ne`首尔、`apac-se`新加坡等 |
| | Globalping 筛选 | CN+datacenter-network | **全局**。下拉：中国 · 云机房 / 中国 · **全部网络**（`CN`，云机房 40 + 家宽 26 共 66 个探针）/ 中国 · 家庭宽带 / 东亚 / 西欧 / 北美，或选「自定义…」填任意 magic |
| | 每次探测点数 | 3 | 三档下拉：`1` 单点采样 / `3` 多数表决 / `5` 更稳；**奇数**才可能不平票；⚠️ 额度按点数计费，`cost = 点数` |
| | IP 版本 | 4 | 4 / 6 |
| | CF 探测超时 | 8000 ms | **只对 cf 后端生效**；也用作「响应偏慢」判定的基线（取其一半） |
| | GP 探针超时 | 15 秒 | **只对 globalping 后端生效**。整数秒 5–30，这是"告知远端探针最多跑多久"，不是"我们等多久"——两条链路的超时互不相通 |
| | 大陆探测臂端点 | 空 | **全局**。逗号分隔的探测臂 base URL，可填多个（**多端点做多数表决**）。空 = 不启用 —— 配了 `cn` 的站点会自动**降级到 CF** 边缘探测（来源标记成 `CF:…（降级）`），不会停摆。⚠️ 端点有两种形态，见「启用大陆探测臂」章 |
| | 探测臂令牌 | 空 | `cn` 探测臂的鉴权令牌（请求头 `x-probe-token`）。**只写不读**：后台只回显掩码，永不回明文 |
| | 探测臂超时 | 8000 ms | **只对 cn 后端生效**。它是"告知探测臂每条最多跑多久"（探测臂侧再钳到 1000–15000），不是"我们等多久"——与 CF / GP 两条链路的超时**互不相通** |
| 证书 | SSL 检测筛选 | CN+datacenter-network | 与站点筛选解耦，避免窄筛选找不到探针 |
| | 每轮补检数 | 2 | 每轮最多为几个站点补检证书，0 = 停用。单站最坏 14 个子请求（1 次发起 + 每 2s 轮询一次，共 25s 窗口；健康站点第 1 次就拿到）。**与探测共用同一份子请求预算**，额度不够时自动顺延到下一轮 |
| | 降级阈值 | 14 天 | 剩余 ≤ 该值判为「降级」；0 = 只在证书已过期时降级 |
| 高级 | 子请求预算 | 30 | **探测 + 证书检测共用**的每轮出网子请求上限（1–35）。免费层硬上限 50，而 D1 往返**另计**约 15–20 次，所以别贴着 50 设。额度用尽的站点会被**跳过**（记进 cron 日志的 `skipped`），而不是把整轮打成失败 |
| | 明细保留天数 | 30 | 过期记录由 cron 每天自动清理 |
| | 最近检查条数 | 20 | 详情页「最近检查」最多列几条（5–200） |
| | 故障记录条数 | 10 | 详情页「故障记录」最多列几条（1–100） |
| 告警 | Webhook 地址 | 空 | 可直接对接飞书 / 钉钉 / Server 酱 |

> **为什么位置（CF 区域组 / Globalping 筛选）是全局而不是每站点一份**：
> 一个站点只会解析出唯一后端，所以两份位置必然只有一份生效 ——
> 另一份是死配置，放出来只会让人误以为能分别控制。

> **为什么 Globalping 默认采 3 个探针（多数表决）**：
> Globalping 把测量派给哪台探针由平台决定，且对同一筛选有**首选项粘性**。
> 单点采样时，那台机器所在链路的一次抖动会被 100% 记成「站点失败」——
> 实测「中国大陆 · 家庭宽带」筛选下单点失败率约 25%，而目标站点完全正常，
> 只是跨境链路的 TLS 握手被概率性丢弃；配上默认 `fail_threshold = 3`
> 就是每天 4~5 次误告警。多探针下失败是**不同步**的（同一次测量里会出现 2 成功 1 失败），
> 于是判定规则是：
> - **多数派即结论**；平票则整次作废、**不写检查记录**（宁可这轮没数据，也不凭空造一个 up/down 出来）
> - `failureSource = internal` 的探针（Globalping 平台自身故障）**剔除、不参与投票**
> - 代表值取多数派内的**中位数**，不取最快 —— 取最快会让页面长期显得比实际更快
>
> 代价是额度按点数计费（`cost = 点数`）：5 分钟间隔的站点是 12 次/小时，
> 免费额度 250/小时下约可支撑 6 个 Globalping 站点，配 token（500/小时）翻倍。
> 档位由后台下拉的 `<option>` 定义（当前 **1 / 3 / 5**），选定即原样生效 ——
> 服务端**刻意不做校验**（要加档位只加一行 `<option>` 即可）。
> ⚠️ 所以若改用环境变量 `GP_LIMIT` 直设，必须取下拉里存在的档位，否则回填时会
> 显示成"非预设档"（不会被静默改回默认，但也不再是常规选项）。
> 没有偶数档是刻意的：2 点的表决平票率就是 1/2，一半次数白花额度还拿不到数据。
> 选 `1` 等于关掉多数表决，回到"单点抖动直接算故障"的老行为（逃生舱）。

## 几点设计取舍

- **探测为什么分两阶段**：Workers 免费计划每次调用最多 50 个子请求，轮询等结果会吃光额度。
  Globalping 改为「本轮发起、下轮收取」，每站点压到 2 个子请求。
- **Globalping 为什么要「提前一个周期」发起**：调度器每分钟醒一次，而两阶段的探测本身就跨
  一个 cron 周期（本轮发起、下一轮才收得到结果）。若等「距上次**结果**满 interval」才发起，
  结果落地会比设定值晚一整轮 —— 1 分钟的间隔实际变成 2 分钟。所以对 Globalping 站点按
  `interval − 1 个 cron 周期` 提前发起，让**结果**落在间隔上；CF 后端同步返回，不做提前。
  另外 `last_checked_ts` 是在探测写库之后才更新的（比 check 本身晚约 1 秒），判定到期时
  留了 15 秒宽容量 —— 否则「间隔 = 1 分钟」会因差 0.7 秒被判成未到期，白等一整分钟。
- **大陆探测臂（`cn`）的取舍**：探测端**只报「HTTP 层通没通」**（`results[].ok`），
  **不做 up/down 判定** —— 判定口径必须全局只有一处（CF 侧 `judge()`），否则「后台手点测」
  与「自动探测」会用两套规则得出不同结论。它相对 Globalping 还有两个特点：
  ① **批量** —— N 个站点一次调用测完，CF 侧整批只花 1 个子请求（GP 是每站点 2 个），站点越多越省；
  ② 多端点时同样走 `gpDecide` 的**多数表决 + 多数派中位数**（单端点自然退化为「1 票即结论」）。
  ⚠️ **端点级失败（连不上探测臂）不写检查记录** —— 与 GP 的 broken / 平票是**同一条约定**：
  我们没拿到数据 ≠ 站点挂了；写失败会凭空推高 `consecutive_fail`、攒够阈值还会误告警。
- **后台为什么要聚合接口**：实测从国内访问 CF 边缘，单个请求 TTFB 中位约 780ms（静态文件、
  走缓存、不进 Worker 也是这个数）——瓶颈在链路，不在数据库。所以优化方向是**减少请求数**，
  后台从串行 3 个请求合并成 1 个 `/api/admin`。
- **密码为什么不做成后台可改**：那样就得在 D1 存哈希、还要处理「改密码如何作废旧会话」。
  密码本质是部署期配置，放环境变量更简单、更容易审计，也省掉一类状态。
  登录用常量时间比较；`ADMIN_PASSWORD` 为空时是**整体停用后台**（403 + 说明页），
  而不是"先开放、页面上提醒你尽快设置"—— 后者等于用一个 5 秒的提示去兜住
  "任何人打开这个网址就能改配置、读到告警 Webhook 与 Globalping Token"。
- **位置为什么是全局而非每站点**：一个站点只解析出唯一后端，两份位置必然只有一份生效。
- **登录限速在 D1 上计数**：低流量下 Workers 经常每次请求都新建 isolate，内存 Map 形同虚设。
- **域名为什么不写进 `wrangler.toml`**：`routes` 是声明式的，一旦写进来，每次部署都会按配置
  重建 DNS 与证书；而控制台手动加的域名是独立持有的路由资源，不在配置里就不会被 wrangler 动。
  交给人工绑定后，换域名不必改仓库、也不必重新部署。
- **所有非 GET 请求为什么要校验同源**：Cookie 是 `SameSite=Lax`，它挡不住"会改状态的 GET 导航"。
  与其依赖"每个写接口都记得写成 POST"，不如统一加一道校验（`Origin` → `Sec-Fetch-Site` → 拒绝）。
- **「最近检查」里看到故障、「故障记录」却是空的**——这不是 bug，是两处口径不同：
  - 「最近检查」是**原始明细**，每一次失败都会列出来（红标「故障」）。
  - 「故障记录」是**故障事件**，把连续失败合并成一段，且只记「连续失败次数 ≥ 该站点阈值」
    的段（阈值 = 站点表单里的「连续失败几次告警」，默认 3）。单次抖动（下一拍就恢复）
    刻意不记，否则每次网络波动都会刷出一条事件。
  - 另外故障记录只统计**当前时间窗**（6 小时 / 24 小时 / 7 天 / 30 天）内的段，
    切到更短的窗口会把历史事件隐藏掉。
  - 段内失败次数由时长估算：`段时长 ÷ 间隔`。`start` 是首个失败点、`end` 是其后第一个成功点，
    所以段时长恰好 = 失败次数 × 间隔 —— **不要再 +1**：那会把「1 次失败」估成 2 次，
    使阈值判定整体少一次，连单次抖动都会被当成故障事件。
  - 想让单次失败也进故障记录：把该站点的阈值改成 1（但这样每次抖动都会触发 Webhook 告警）。
- **30 天色条的颜色跟「故障记录」同一口径**（绿 = 全天正常、黄 = 当天只有零星抖动、
  红 = 当天出现过真故障）。
  - 早先的实现是「当天只要有失败就涂红」，这就跟「故障记录」自相矛盾了：同一次单点抖动，
    一处刻意不记（未达阈值），另一处却标成红色故障。现在红只留给
    **连续失败次数 ≥ 该站点阈值** 的天，未达阈值的标黄（`blip`）。
  - 「连续」只能靠时间戳间隔判断（两次失败的时间差 ≤ 1.3 × 间隔即视为相邻）。
    容差取 1.3 倍而不是更大，是为了保证 **< 2 倍间隔** —— 否则会把「中间夹着一次成功」
    的两次失败并成一段，把零星抖动误判成故障。跨天的段按天切开，属保守处理。
  - 判据只读**失败行**（走 `(ok, ts, site)` 索引），读取量与该段时间的失败次数成正比，
    而不是与总检查数成正比。

## 本地开发

```bash
npm install     # 装 wrangler（唯一 devDependency）
npm run dev
```

默认 `http://localhost:8787`。`npm run dev` 会先在本机的 D1 副本上建表再启动，直接可用。

> **本地也要管理员密码**：鉴权是 fail-closed，不给本地留特例 —— 否则很容易变成
> "本地能进后台、部署上去进不去"这种最难查的不一致。项目里有一份 `.dev.vars`
> （已被 `.gitignore` 排除）写了 `ADMIN_PASSWORD=dev`，本地登录就用 `dev`；
> 想换别的值改这个文件即可，改完重启 `npm run dev`。

> `npm install` 建议不要跳过：`scripts/setup-d1.mjs` 优先用本地的 wrangler，
> 只有本地没装时才退回 `npx`，而 npx 缓存损坏过（缺 `ws` 模块）。

### 命令一览

| 命令 | 作用 |
|---|---|
| `npm run dev` | 本地起服务（先给本机 D1 副本建表） |
| `npm run deploy` | 准备生产库 + 部署生产 |
| `npm run deploy:preview` | 准备预览库 + 部署预览 |
| `npm run setup` | 只准备生产库，不部署 |
| `npm run setup:preview` | 只准备预览库，不部署 |
| `npm run sw:bump` | 单独重写 Service Worker 版本号 |

四个部署/准备类命令都会自动完成「建库 → 写绑定 → 建表 → 校验结构」，
区别只在于目标是生产还是预览、以及最后是否执行 `wrangler deploy`。

其它常用：

```bash
npx wrangler secret put ADMIN_PASSWORD      # 设/改管理员密码
npx wrangler d1 execute uptime-db --remote --command "SELECT COUNT(*) FROM sites"
npx wrangler tail                            # 看实时日志
```
