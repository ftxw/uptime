uptime 监控 · 问题诊断与架构方案

针对「探测不稳 / 国内延迟不准 / 是否迁移 Makers / 秒级定时精度」四项诉求的评估与落地建议
代码基线：Cloudflare Workers + D1 + Durable Object 评估日期：2026-10-14 结论：不建议整站迁移，建议「双引擎」

一句话结论：你现在遇到的四个问题，本质上是两个平台能力的错配——「秒级精确定时」是 Cloudflare 的强项（Durable Object Alarm），「中国大陆境内探测点与国内访问速度」是 EdgeOne Makers 的强项（大陆多地域 Cloud Functions）。把两件事分别放到擅长它的平台上，四个问题可以一次性解决。

而整站迁移到 Makers 不成立：免费版定时任务最小间隔是 1 天，且平台没有关系型数据库（只有 KV / Blob），你现在这套 7 表 + SQL 聚合的读路径无处安放。

一、现状诊断：问题定位到代码

1.1 为什么 CF Durable Object 探测不稳

不止一个原因，是四件事叠加：

每轮都在冷启动
src/index.js 的 probeViaCf() 在 finally 里无条件调用 stub.kill()。除了省 duration 费，代价是每一轮探测都从零唤醒一个 DO 实例——冷启动本身就是一个失败窗口。而且 kill() 靠 blockConcurrencyWhile 内抛错来终止实例（src/prober.js 自己也标注了「这是 hack」），属于非文档化行为，不受平台保证。
根本没有大陆出口
locationHint 只接受粗粒度区域组，APAC 实测只能拿到 apac→HKG / apac-ne→ICN / apac-se→HKG。也就是说你的 CF 探测全部是从香港/首尔出发打大陆站点——跨境链路上 GFW 概率性丢包、TLS 握手被丢、目标站 WAF/CDN 对境外 IP 限速，都会直接变成一次「请求超时 / 连接被重置」。这就是失败率的直接来源。
子请求额度把预算压到很难受
免费层单次调用上限 50 个子请求，而 D1 往返也计入（实测 15~20 次）。所以 subreq_budget 只能设到 30，站点一多就进 skipped —— 静默跳过、不报错，表现就是「某些站点明明没挂，但一直没有新数据」。
cron 本身就不是精确时钟
官方明确：cron 触发「在计划分钟附近几秒内」、Worker 被调度到「利用率较低的机器」上执行，且不保证毫秒级精度。此外 cron 是 UTC、免费层每次 CPU 仅 10ms、触发器变更最长要 15 分钟才全网生效。一整轮 cron 失败就是那一分钟彻底没数据，而系统里没有补跑机制。

1.2 为什么 Globalping 不稳

  • 探针派发不可控：平台决定把测量派给哪台机器，且对同一筛选条件有首选项粘性。反复测量会被反复派给同一台 —— 那台机器链路一抖，该站点就稳定误判。
  • 大陆家宽跨境链路天生不可靠：你自己的注释里已经记录了实测数据——「中国大陆 · 家庭宽带」下单点失败率约 25%，抓到的原因是 tls: null（TLS 握手一个字节都没回来），并且平台在 15001ms 硬切。这不是配置问题，是链路性质。
  • 两阶段 + 单行 pending 有静默停摆风险：dispatch() 里 if (pendingSet.has(s.id)) continue —— 只要一条 pending 收不到（measurement id 失效、API 抖动），该站点就不再被发起探测，只能靠 PENDING_TTL_MS = 180s 兜底。这是你代码注释里已经识别出来的坑，说明它确实发生过。
  • 「没结论」被丢弃 → 数据稀疏：broken 分支、平票、全 internal 故障，都刻意不写检查记录（这个设计是对的，不能凭空造一个 up/down）。但次数一多，用户在页面上看到的就是「经常没有数据」，主观上等同于「经常失败」。
  • 免费额度很容易打满：额度按探测点数计费（cost = limit）。limit=3 时，5 分钟间隔的站点 = 36 cost/小时/站 → 免费 250/h 只够 约 6 个站点，带 token（500/h）约 13 个。超额 → 发起失败 → 自动降级到 CF 路径 → 于是又回到 1.1 的问题。

1.3 为什么国内延迟测不准

根因只有一句话：测量点在哪里，数值就代表哪里。

  • Cloudflare 在中国大陆没有可用的计算节点。CF 的中国区网络是通过京东云等合作方承载的、面向企业的独立能力，需要单独开通，Workers / Durable Objects 的正常部署不会落在大陆。所以你的「CF 探测」本质上是境外视角。
  • Globalping 有大陆探针，但成分不适合测延迟。以家宽和中小机房为主，且跨境链路抖动本身就大 —— 数值偏高、方差大。把这种数据画成「延迟趋势图」，趋势里混进的是国际链路噪声，不是站点性能。
  • 你代码里的 slowBaseMs() 已经因为这件事给两个后端分别设了不同的基线（GP 用 15s、CF 用 8s），注释里也写了「拿 8s 的一半去卡 GP 站点会把大量健康站点长期标成偏慢」。这说明现象早就被观察到了，只是当时只能「各自放宽阈值」绕过去。

结论：想要「对国内站点相对准确的延迟」，探测点必须满足两个条件——位于中国大陆境内，且有多个不同地域互为参考。这两条 CF 都给不了。

二、四条硬约束（决定了方案的可行边界）

下面这些是平台级事实，先钉死，后面所有方案都在这张表里做取舍。

约束事实对方案的影响
Cloudflare cron 粒度 5 段 cron，最小 1 分钟；触发「在计划分钟附近几秒」；不保证毫秒精度；UTC；免费层每次 CPU 10ms。 做不到按站点锚定的秒级定时（如 10:39:18 → 10:44:18）。
Cloudflare 大陆节点 Workers / DO 不落中国大陆；中国区走合作方、企业专属。 做不到境内视角的延迟测量。
Cloudflare DO Alarm setAlarm(毫秒时间戳)，可编程、精度远高于 cron；at-least-once 保证，失败自动指数退避重试（2s 起、最多 6 次）；DO 数量不限，每个对象可各挂一个 alarm。 正解CF 侧唯一的秒级调度解，也是「每站点独立锚定」的天然载体。
Makers 免费版定时 edgeone.json 的 schedules 支持标准 5 段 cron、可指定 IANA 时区，但免费版最小执行间隔为 1 天（cron 表达式本身支持到分钟，限制在免费档）。 做不到用 Makers 原生定时器跑 1~5 分钟的监测周期。
Makers 存储 只有 KV（1 GB，单值 1 MB）与 Blob（1 GB，单值 25 MB）；没有关系型数据库、没有 SQL。 需重写现有 7 表 + GROUP BY date / P95 偏移 / LAG() 窗口函数的读路径。
Makers Cloud Functions 地域 大陆可选：广州 / 上海 / 南京 / 北京 / 成都；海外可选：新加坡 / 香港 / 曼谷 / 雅加达 / 首尔 / 东京 / 法兰克福 / 弗吉尼亚 / 硅谷。每个项目只能配一个大陆地域。 关键能力多地域探测 = 开多个 Makers 项目。
Makers Cloud Functions 限制 单次最长 10–120s（默认 30s，可配）；Node.js 20；请求/响应体 6 MB；100 万次/月；CPU 不按 200ms 计（那是 Edge Functions 的限制）。 够用一次调用探测几十上百个目标没有压力。

三、Makers 可行性：逐条回答你的第 3 问

你的诉求Makers说明
网站加载速度快可行EdgeOne 有大陆节点，国内访问显著优于 CF（你 README 里记的「国内访问 CF 边缘 TTFB 中位约 780ms」）。免费版含自定义域名 + 免费 SSL。
数据加载速度快有条件只读数据可以放 KV/Blob 走边缘读，非常快；但只要涉及聚合查询（30 天色条、P95、窗口函数），就必须改成「写入时预聚合 + 读现成结果」。
对国内站点的延迟准确强项大陆多地域 Cloud Functions = 境内打境内，这是目前唯一能自建且真正准确的路。
监测时间精确到秒（站点级锚定）不行平台没有秒级/亚分钟定时器；免费版 cron 最小间隔 1 天。要秒级锚定必须靠外部触发器，而精度上限就被外部触发器锁死了。
整体迁移成本偏高数据层要从 D1/SQL 重写成 KV/Blob；定时要从 cron 改成外部触发。等于重写一半后端。

结论：Makers 不适合当这套系统的「大脑」（定时 + 数据），但非常适合当它的「中国大陆探测臂」。所以推荐方案是——两件事分开，各放各的强项平台。

四、推荐方案 A：双引擎（CF 控制面 + EdgeOne 大陆探测面）

4.1 架构

访问层 · 国内用户
EdgeOne 静态站点前台页面，大陆边缘直出
只读快照接口读 EdgeOne KV，不跨回 CF
CF 源站（兜底）后台 / 写操作仍走 CF
调度层 · Cloudflare（秒级、站点级锚定）
SchedulerDO（单例）storage.setAlarm()，毫秒级

at-least-once + 退避重试不再依赖 cron
探测层 · 双后端 + 多数表决
大陆探测集群（主）Makers 北京 / 上海 / 广州

4.2 关键改造点（按文件给）

① 调度：cron → DO Alarm（解决「秒级精度」+ 一半「稳定性」）

  • src/scheduler.js（新增）：SchedulerDO 单例，idFromName('scheduler')。
  • storage 里维护每站点 { id, intervalMin, anchorTs, nextDueTs }。首次入库时 anchorTs = 首次实际探测时刻，之后 nextDueTs = anchorTs + n × intervalMs —— 天然满足「10:39:18 → 10:44:18」，因为它只跟自己的锚点算，永远不跟整分钟对齐。
  • alarm() 里取出所有 nextDueTs <= now 的站点 → 分组派发 → 每站把 nextDueTs += intervalMs → 再 setAlarm(min(nextDueTs)) 自调度。一个 DO 就能承载所有站点的秒级定时。
  • wrangler.toml：[triggers] crons 可以保留一条低频兜底（例如每 10 分钟扫一次，修复异常）或直接删除。
  • src/index.js 的 dueSites() / DUE_GRACE_MS 这套「按分钟判定到期」的逻辑可以退役 —— 它存在的唯一理由（cron 只能每分钟醒）消失了。
  • 额外收益：alarm 有 at-least-once + 指数退避重试，比 cron「丢了就丢了」强一个量级。

② 探测：新增 probe_kind = 'cn'（解决「国内延迟准确」+ 另一半「稳定性」）

  • Makers 侧：cloud-functions/api/probe.js，暴露 POST /api/probe。入参 { items: [{ url, keyword?, timeoutMs }] }（最多 50 条），出参 { ok, region, ts, wallMs, results: [{ url, ok, status, ttfb, total, bytes, keywordHit, errorCode, error }] }。用 fetch + AbortController 测 TTFB；Node 侧可以读响应正文，所以关键字校验对国内站点是真实生效的（这是 Globalping 后端做不到的）。
    ⚠️ 这里刻意不做 expectCodes 判定：results[].ok 只表示「HTTP 层跑通没跑通」，up/down 的判定仍然只在 CF 侧用现有的 judge() 做。判定口径必须全局只有一处，否则「后台手点测」与「自动探测」会得出不同结论。实际落成的契约见附录 C。
  • Makers 项目：edgeone.json 里 cloudFunctions.mainlandRegions 分别配 ap-beijing / ap-shanghai / ap-guangzhou。一个项目只能配一个大陆地域，所以要开 3 个项目（免费版项目上限 40，够）。
  • CF 侧：src/probe.js 新增 probeViaCn(env, sites)，按地域分组并发调用 3 个端点；判定直接复用你已有的 gpDecide() —— 把「多探针多数表决 + 中位数代表值」那套逻辑原样用在「多地域」上，代码几乎不用改。
  • src/settings.js 新增：cn_probes（端点列表）、cn_regions_per_check（1 或 3）、cn_timeout_ms。
  • 失败处理：任一地域失败 → 用剩余地域继续表决；全部失败 → 自动降级到 CF 边缘（沿用你已有的 fallback 标记与 source 格式）。

③ SSL 检测：从 Globalping 换成 Makers（顺带去掉一大块不稳定）

  • Node 运行时可以用 node:tls 的 tls.connect() + socket.getPeerCertificate(true) 直接拿到完整证书链（颁发者、有效期、SAN、密钥类型），不需要依赖 Globalping 的 HTTP 测量。
  • 放在同一个 Cloud Function 里（POST /api/ssl），与探测共享出口。好处：不再受 Globalping 探针粘性影响、不再跨境、不再消耗 GP 额度。
  • Globalping 退化为「可选备用后端」，甚至可以从默认配置里摘掉。

④ 前端加速：只读快照下发到 EdgeOne（解决「网站与数据加载快」）

  • CF 侧每分钟把 /api/overview 的紧凑 JSON（几十 KB）PUT 到 Makers 的一个 KV namespace。
  • EdgeOne 侧用 Edge Function 读 KV 直出 —— 国内首屏完全落在大陆边缘，一次都不跨回 CF。
  • 静态页面（public/）也镜像一份到 EdgeOne 项目。
  • 写操作、后台、详情页历史查询仍回 CF/D1（这些是低频操作，慢一点可接受）。

⑤ 数据层：不动

D1 的 7 张表与索引全部保留，checks.source 记 cn:ap-beijing，checks.probe 记地域与出口 IP。origin.js 的 formatOrigin() 加一个 cn: 前缀的格式化分支即可。

4.3 为什么这样能满足你的四条诉求

诉求由什么解决
探测稳定3 个大陆地域冗余 + 多数表决；DO Alarm 的 at-least-once 与自动重试；去掉「每轮 kill 冷启动」；不再受 cron 抖动与整轮失败影响；失败自动降级 CF 边缘。
国内延迟准确探测点在北京 / 上海 / 广州的大陆机房，境内打境内。跨地域中位数比单点更接近「国内用户体验的中位水平」。
网站与数据加载快页面与只读快照都落在 EdgeOne 大陆边缘节点直出，不再跨境回 CF。
秒级精确到秒DO Alarm 毫秒级时间戳 + 站点级 anchorTs：10:39:18 建立锚点，之后每个周期都落在 :18 秒，不受整分钟约束。

4.4 风险与必须实测的点

这是全方案唯一的关键风险：CF（香港/新加坡边缘）主动 HTTP 调用大陆 Makers 端点，链路是否够稳。

请求路径是：CF 边缘 → https://<项目>.edgeone.app/api/probe（EdgeOne 边缘）→ 转大陆 Cloud Function → 探测目标。其中「CF → EdgeOne 边缘」这一段要跨境。测出来的延迟是大陆函数 → 目标站的，所以数值本身准确；但控制链路的成功率必须实测。

如果这一段不稳，退路有三条：① 让 Makers 侧主动拉取（但 Makers 定时最小 1 天，需要在 CF 侧放一个极轻的拉取/回调，退化为「探测仍准确、调度精度仍在 CF」）；② 用一个第三方廉价的分钟级触发器（cron-job.org / GitHub Actions / 一台 2 美元 VPS）触发 Makers，Makers 探测完回调 CF 写入；③ 只把「探测」留在 Makers，调度与写入仍由 CF 用 CF 自身的国际出口完成 —— 本质上就是方案 ① 的变体。

另外三项建议一并实测：

  • DO Alarm 的实际精度：连续记录「计划触发时间 vs 实际执行时间」24 小时，确认抖动在可接受范围。
  • Makers 免费额度：单站点一周期 3 地域 = 3 次函数调用。以 20 个站点、5 分钟间隔估算：20 × 12 × 24 × 3 ≈ 17,280 次/天 ≈ 52 万次/月，免费额度 100 万次/月 —— 够，但余量不算大，站点多了要留意。
  • 多项目维护成本：3 个大陆地域 = 3 个 Makers 项目（免费版上限 40）。建议把这 3 个项目做成同一份代码、只改 edgeone.json 的地域字段。

五、备选方案 B：纯 CF 加固（不引入第二个平台）

如果你的取舍是「不想多维护一个平台」，那就只解决问题 1 和 3，问题 2 只能靠外部数据源补。

项做法
秒级调度同上：cron → DO Alarm。这一条在 CF 上完全成立，是 CF 自身的强项。
稳定性去掉每轮 kill()；探测失败加重试与退避；多 hint 冗余（apac + apac-ne 各跑一份取多数）；把 subreq_budget 提到 45 并压缩 D1 往返次数；把 SSL 检测与探测拆成两个独立的 Worker（各自独立 50 子请求额度）。
Globalping 若保留gp_limit 提到 5；筛选只用 datacenter-network（避开家宽跨境 TLS 丢包）；pending 加「最多重试 2 次再丢弃」；加额度预警。
国内延迟CF 自身无解。三条外挂路径：
① EdgeOne Makers 大陆云函数（即方案 A 的探测臂，只接一根线）
② 阿里云函数计算 FC（北京/上海/深圳等地域固定，同样能做探测臂，见附录 A.2）
③ Globalping 大陆「机房网络」探针（免费，但就是你正在受的苦，只能缓解）
④ 付费拨测：腾讯云拨测 / 听云 / Better Stack / Uptime.com。⚠️ 阿里云 ARMS 云拨测已停止新开通（官方公告：自 2024-06-01 起不再支持开通按量付费与购买预付费资源），别把它算进候选。

适合谁：只想小步快跑、不想碰前端与数据层、能接受「中国大陆延迟依赖外部数据源」。

六、备选方案 C：整站迁移 Makers（不推荐）

维度迁移后
国内访问速度明显改善
国内延迟准确度明显改善（大陆 Cloud Functions）
分钟级定时丢失免费版 schedules 最小间隔 1 天，必须外挂触发器，且秒级锚定的上限被外挂触发器锁死。
数据查询能力丢失无 SQL。要么把 30 天色条 / P95 / 故障事件全部改成写时预聚合，要么外接数据库（Turso / Supabase / 自建）——后者又把延迟与运维成本加回来。
改造量数据层与调度层等于重写，前端要适配 KV/Blob 读模型。

结论：除非你打算用 Makers 付费版（分钟级 cron 可能可用）并且接受外接数据库，否则整站迁移是用两个新的硬约束去换两个已经能单独拿到的好处，不划算。

七、落地步骤建议

  1. 第 0 步 · 可行性实测（最重要，半天）

    这一步的结论直接决定后面走方案 A 还是方案 B。
  2. 第 1 步 · 调度换血：CF 侧把 cron 换成 SchedulerDO + Alarm，探测逻辑先不动。观察 24 小时的定时精度与失败率变化。

  4. 第 3 步 · SSL + 前端：SSL 检测换成 Node tls 直取；页面与只读快照镜像到 EdgeOne。
  5. 第 4 步 · 收尾：Globalping 降为可选备用；更新 README 与后台设置项文案。

八、需要你确认的三件事

  1. 是否接受引入 EdgeOne Makers 作为「大陆探测臂」？这是解决国内延迟准确度的唯一自建路径。不接受的话，方案 B 里只能走付费拨测。
  2. 是否有 Makers 付费版？如果有，分钟级 cron 可能可用，调度部分可以简化（但秒级锚定仍然要靠 DO Alarm 或类似机制，cron 本身给不了任意秒）。
  3. 前端是否愿意也镜像到 EdgeOne？这是「国内打开快」的关键；如果前台必须留在 CF，那么只能改善 API 响应，页面本身仍受跨境 TTFB 拖累。

附录 A：其他平台逐一对标（2026-10-14 补充）

补充回答「阿里云 ESA 能否实现」以及相关平台的对照。结论先给：ESA 能承担「前端加速 + 只读数据边缘直出」，但承担不了「调度器」和「探测执行体」；阿里云侧真正对应方案 A 探测臂角色的是函数计算 FC，不是 ESA。

A.1 阿里云 ESA（边缘安全加速）

ESA 的产品定位是「安全 + 加速 + 边缘计算」，其中边缘计算部分是「函数和Pages」（V8 隔离的 JavaScript 边缘函数 + 静态站点托管）。逐项对照后，有三条是回避不掉的硬限制：

限制项官方值对我们的影响
单次执行子请求数4 个一次函数执行最多发 4 个 fetch。你一轮要探测 N 个站点、每站至少 1 个子请求，4 个就是天花板，除非把探测拆成大量一次一个的调用 —— 但那又需要有人负责扇出与汇总。
网关等待时间10 秒超过 10 秒没有任何数据返回，网关直接断开并返回 504。慢站点、超时站点会连结果都拿不到。
定时触发器无官方文档里「函数和Pages」只有域名绑定与路由两种触发方式，没有 cron。同一技术体系下（阿里云 AOne 边缘函数）的定时触发器还标注为「即将上线」。所以它不能自己跑监测循环。
响应时间上限120 秒含 I/O 等待，不是瓶颈。
CPU 规格5 / 50 / 100 ms探测是 I/O 密集型，够用。

边缘存储 EdgeKV单账号 10 GB、单空间 1 GB、单 Key 512 B、单值 1.8 MB只读快照（几十 KB）放得下。但最终一致性为几秒到十几秒、最迟 300 秒，实时性比 D1 差一档。
数据库无关系型数据库只有边缘 KV，SQL 聚合无处安放。

还有一条最关键、最容易忽略的限制：ESA 边缘函数执行在「接收到请求的那个 POP」，而不是指定地域。

也就是说，如果由 CF（香港边缘）去调用你的 ESA 函数，请求会在香港 POP 执行 —— 探测到的依然是境外视角，用它做大陆探测点并不可靠。要让它在大陆执行，就只能由大陆的客户端发起请求，而「需要一个大陆的发起方」恰恰是我们要解决的问题本身。

对比之下，EdgeOne Makers 的 Cloud Functions 与阿里云函数计算 FC 都是「部署到指定地域」：请求从哪进来无所谓，函数一定在 ap-beijing / ap-shanghai 等指定地域执行。这个差别决定了谁能当探测臂。

A.2 阿里云函数计算 FC —— 阿里云侧真正能当「探测臂」的组件

如果你倾向留在阿里云生态，那对应方案 A 里「大陆探测集群」的正确组件是函数计算 FC，而不是 ESA：

  • 定时触发器最小 1 分钟，且官方明确「无法实现精确到秒级的定时触发」—— 所以它做不了秒级调度，但做「被调度方」没问题。
  • 地域可选北京 / 上海 / 深圳 / 杭州 / 张家港 / 成都 等，地域固定，可以做大陆多地域探测点。
  • 运行时 Node.js / Python / Go，没有「4 个子请求」这种限制，一次调用可以批量探测几十个目标；可挂 VPC 连 RDS / Tablestore / Redis。
  • 定位：能替代 Makers 做探测臂，但不能替代 DO Alarm 做秒级调度。

A.4 结论

  1. 只靠 ESA 实现不了这套系统。三个不及格项：没有定时触发器（不能自跑循环）、单次仅 4 个子请求（一轮探不了几个站）、无关系型数据库；再加上「按接入 POP 执行」导致它无法充当大陆探测点。
  2. 「全阿里云」可以做出一个可用版本：ESA 做前端加速 + 只读快照，函数计算 FC 做探测执行，Tablestore / RDS 做数据 —— 定时触发器最小 1 分钟且官方明确不支持秒级；秒级锚定只能用 FC 的「延迟调用」自己搭链（见 A.5），比 DO Alarm 脆弱。
  3. 最优解仍是双引擎：调度留在 Cloudflare（DO Alarm 是四个平台里唯一能干净给出秒级锚定的机制 —— at-least-once + 自动指数退避重试），探测交给地域固定的大陆云函数。探测臂用 EdgeOne Makers 还是 阿里云函数计算 FC，取决于你更愿意维护哪个生态 —— 两者在「探测臂」这个角色上能力相当。

能不能直接部署？分两层看

  1. 现有 CF 项目不能直接搬过去。FC 只提供「函数执行」这一件事：没有 D1（SQL 聚合）、没有 Durable Object（秒级 alarm）、也没有静态站点托管（静态资源要另配 OSS + CDN，或走 ESA 的 Pages）。所以「整站部署到阿里云函数」这个选项不存在，必须改造。
  2. 但「大陆探测臂」这个角色可以、也适合部署到 FC。写一个 HTTP 函数：接收站点列表 → 并发探测 → 返回结果数组。部署方式有三种：
    • 控制台：创建函数 → 选 Node.js / Python / Go → 上传代码或 ZIP → 加 HTTP 触发器。适合一次性部署。
    • Serverless Devs CLI：s init 初始化 → s deploy 一键部署。适合可重复部署与 CI/CD。
    • 应用中心：选模板一键部署，适合先跑通再改造。
  3. 落地时必须注意的几处：
    • HTTP 触发器与其他类型触发器互斥 —— 同一版本/别名下最多一个 HTTP 触发器，且设置 HTTP 触发器后不能再挂其他类型触发器。所以「被 CF 调用的探测函数」与「自己定时跑的调度函数」要拆成两个函数。
    • 内置域名（*.aliyuncs.com）仅用于测试，对外提供网站类服务需用已备案的自定义域名；内置域名还会在响应头强制加 content-disposition: attachment（纯 API 调用不受影响）。
    • VIP 会不定期轮换 —— 不要把解析出的 IP 硬编码，始终用域名调用。
    • 冷启动：低频函数首次调用有几百毫秒到秒级的冷启动。它不影响测量值（TTFB 是在函数内部计时的，冷启动只发生在函数自己启动时），但会拖慢控制链路。可用「最小实例数 ≥ 1」消除，代价是无请求时进入浅休眠仍持续计内存费。
    • 弹性实例默认有公网出口，出网流量单独计费。

一个额外发现，它会修正 A.4 的结论：FC 支持「延迟调用」，且精度到秒。

异步调用时可在请求头带 x-fc-async-delay，取值范围 0–3600 秒，函数计算会在该延迟之后触发函数执行。

这意味着理论上可以构造一条「函数跑完 → 异步延迟 N 秒调用自己」的自调度链，从而在 FC 上近似实现秒级锚定（首跑 10:39:18 → 延迟 300 秒 → 下一次 10:44:18）。但三点代价必须清楚：

  1. 延迟上限 3600 秒，监测间隔超过 1 小时就断链；
  2. 没有 at-least-once 保证 —— 异步调用失败或链路中断时自己不会知道，必须额外加一个「看门狗」（例如每分钟跑一次、检查 last_run_ts，发现超期就重新点火）；
  3. 每次自调用都多一跳调用费用。

结论：能做，但明显不如 DO Alarm 干净（后者是平台级 at-least-once + 失败自动指数退避重试）。如果你本来就打算用阿里云全家桶，这条路可以走；否则不必为了它放弃 DO Alarm。

A.6 部署单元：一个地域是不是就得多部署一份？

是。两个平台都是「地域级资源」模型 —— 一个大陆地域就是一份独立部署。区别只在于「配置文件要几份」：

平台一个地域 = 什么多地域怎么推
EdgeOne Makers 一个项目。edgeone.json 的 cloudFunctions.mainlandRegions 数组只能放一个地域 ID（官方明确说明），所以 3 个大陆地域 = 3 个项目。 3 个项目共用同一份代码，只有 edgeone.json 里那一行地域不同；可以写脚本按地域列表生成配置后循环部署。免费版项目上限 40，够用。
阿里云函数计算 FC 一份函数资源。地域是资源级隔离 —— 官方口径是「跨区域部署在技术上本身受限」，北京的函数与上海的函数是两个独立资源，各自有触发器、配置、域名。 Serverless Devs 支持一次推多地域：s.yaml 里把 region 写成 ${env('REGION')}，外面用 shell 循环 export REGION=$r; s deploy -y；或者每个地域一个 yaml（s-hangzhou.yaml / s-xinjiapo.yaml）。所以「配置文件」可以只有一份模板。

但先别急着铺 3 个地域 —— 建议从 1 个起步。

理由：真正的误差分界线是「境内 vs 境外」，不是「北京 vs 上海」。北京到上海的骨干网 RTT 大约 25–30 ms；而香港到北京的跨境链路通常是 50–200 ms 且抖动剧烈，还有 GFW 概率丢包。所以把探测点从 HKG 挪到任意一个大陆地域，就已经消掉了绝大部分问题。

多地域的真实价值只有三条：① 冗余（某个地域抽风不影响监测）② 多数表决过滤单点链路抖动 ③ 削弱单一接入网络的偏差。另外要注意 地域 ≠ 运营商 —— 云厂商同一地域的出口通常本身就是 BGP 多线，单地域已经覆盖了电信/联通/移动；多地域买到的是「多地视角」，不是「多运营商视角」。

建议节奏：1 个地域验证 → 有明确需求再扩到 2 个（一南一北，如北京 + 广州）→ 才考虑 3 个。补充一点：单地域部署在底层已经是多可用区自动容灾，本身并不是单点机器。

把「多地域」做成低维护成本的三个做法：

  • 地域列表只存一处（仓库里的 regions.json 或 CI 变量），部署脚本读它循环，避免「改了 3 个地方漏了一个」。
  • 代码零改动：探测函数从运行环境读自己的地域标识（FC 可用 REGION_ID 环境变量，Makers 侧可读环境变量注入），不为每个地域维护一份代码。
  • CF 侧用环境变量存端点列表（如 CN_PROBES，逗号分隔的 URL 列表），增删地域不改代码；判定逻辑对「N 个端点」通用，N=1 时自动退化为直接判定，不需要两套逻辑。

附录 B：第三方探测 API 备选清单（2026-10-14 补充）

B.1 Globalping：走机房确实更稳，而且这是官方推荐做法

Globalping 的探针带两类网络标签：eyeball-network（ISP 家宽 / 小企业线路）与 datacenter-network（机房）。官方文档在「Uptime monitoring use cases」一节里的原话是：

“Filter for datacenters: When targeting specific regions or countries, append the +datacenter-network filter to ensure probes are running from stable infrastructure.”

更稳的原因有三条：

  • 机房探针有稳定带宽与固定 IP，TLS 握手不会像家宽那样被概率性丢弃；
  • Globalping 对探针有定期质量控制：探针必须通过测试（官方描述为「connected to a reasonably stable network without packet loss」），不通过的会被自动下线；版本过旧的会被强制更新后才可用；被检测到走 VPN 的会被封禁；
  • 滤掉家宽之后，探测结果里不再混入「国际链路抖动」这种与站点本身无关的噪声。

但要清楚：即使全走机房，仍有四类不确定性无法靠这个开关消除。

  1. 首选项粘性：平台会把同一 magic 的测量反复派给同一台探针 ⇒ 单点抖动被放大。这要靠多点表决（gp_limit）压制，不是靠机房标签。而且探针不暴露 UUID，你无法指定只用某台。
  2. Best-effort，不保证数量：官方明确「请求 N 个探针，不保证返回正好 N 个」—— 探针随时可能因为自动更新或质检失败而不可用。
  3. 平台自身故障：failureSource: internal。你代码里已经把它剔除出表决，这个处理是对的。
  4. 额度：免费 250 次/小时，注册后 500 次/小时；额度按 cost = limit 计费，5 分钟间隔的单个站点每小时消耗 12 × limit。所以 limit=3 时 500/h 只够约 13 个站点；提到 limit=5 就只剩约 8 个。

结论：你的默认配置其实已经是机房了（settings.js 里 gp_magic 的默认值就是 CN+datacenter-network）。如果现状仍不稳，主要矛盾多半在额度与平台侧，而不在「家宽 / 机房」这个开关上。

Site24x7 北京 · 上海 · 广州 · 青岛 · 成都 有 API 商业订阅。主张「由外而内」的用户视角监测。
Uptrends 宣称 229 个城市，是否含中国大陆节点需自行确认 有 API 30 天免费试用、无需信用卡 —— 适合先验证再决定。
UptimeRobot / Pingdom / Better Stack / StatusCake 基本没有中国大陆节点 有 API 做全球可用性监测可以，但测不出国内用户视角的延迟，对本项目价值不大。

B.3 成本 / 工作量对照 —— 决定「什么时候真的该自建」

方案月成本工作量秒级锚定
Globalping 调参0 元改 3 个设置项否
腾讯云 CAT（3 节点 / 5 分钟）≈ 780 元对接 OpenAPI否 最小 1 分钟
Dotcom-Monitor / Site24x7订阅制（通常几十至几百元）对接 API否
自建云函数（Makers / FC）≈ 0 元（免费额度内）写探测函数 + 部署需配合 要 CF DO Alarm
自建一台国内轻量服务器≈ 24–60 元写一个常驻进程是 天然支持

一个反直觉但值得注意的结论：在「自建」这一类里，最便宜且能力最全的其实是一台国内轻量服务器，而不是云函数。

一台 ¥24–60/月的国内小机器同时解决三件事：① 大陆探测点（境内打境内）② 无子请求数量限制 ③ 秒级定时 —— 常驻进程里用 setTimeout 或 systemd timer 维护每个站点的 nextDue，天然就能锚定到 10:39:18 → 10:44:18，甚至不需要 DO Alarm 配合。成本还低于商业拨测。

代价只有一条：多一台机器要维护（系统更新、进程守护、单点）。可以先用一台起步，需要冗余时再加第二台。

B.4 建议的推进顺序（每一步都能独立停下来）

  1. 第 1 步 · 零成本先榨干 Globalping（今天就能做）。确认 gp_magic 是 CN+datacenter-network、gp_limit 提到 5、设上 GLOBALPING_TOKEN、给 pending 加重试。观察 48 小时的失败率与数据密度变化。这一步不解决国内延迟的视角问题，但能显著降低「明明站点正常却记成失败」的噪声。
  2. 第 2 步 · 用免费试用验证「境内节点」到底值多少。开腾讯云拨测 CAT 的 15 天免费试用（5 个任务 / 5 分钟 / 6 个节点），拿同一批站点和 Globalping 的数据并排比。这一步花的只是时间，但能让你判断「付费拨测」值不值，以及「自建探测臂」大概能拿到什么样的数。
  3. 第 3 步 · 才轮到自建。到这一步再在两个形态里选：
    · 云函数（Makers / FC）：免运维、免费额度内，但要靠 CF DO Alarm 才能拿到秒级；
    · 一台国内轻量服务器：约 30 元/月，常驻进程天然秒级、无子请求限制，代价是要维护一台机器。

C.1 实际落成的接口契约

接口入参出参
POST /api/probe{ items: [{ url, keyword?, timeoutMs? }] }，最多 50 条{ ok, region, ts, wallMs, results: [{ url, ok, status, ttfb, total, bytes, keywordHit, errorCode, error }] }
POST /api/ssl{ items: [{ url, timeoutMs? }] }，最多 50 条{ ok, region, ts, results: [{ url, authorized, protocol, issuer, subject, key_type, expires_at, days_left, fingerprint256, error }] }
GET /api/ping—{ ok, service, region, requestId, ts, egressIp }

三个接口统一用请求头 x-probe-token 鉴权，且是 fail-closed：未配置 PROBE_TOKEN 时一律返回 503（避免把探测臂变成任人可用的开放代理）。
没有任何接口做 up/down 判定 —— results[].ok 只表示 HTTP 层是否跑通，判定统一在 CF 侧的 judge()。

C.2 与计划的偏差（三处，都已适应）

项计划实际原因
运行地域 ap-beijing ap-guangzhou edgeone.json 的 mainlandRegions 未生效 —— 首次部署时平台报「项目已存在」，地域看来是**项目创建时决定**的。已把配置文件改成与事实一致，不留错误声明。广州同样在大陆，境内视角这个目标不受影响。
访问入口 直接调用 需绑自定义域名 EdgeOne Makers 的自动域名带访问鉴权：不带 eo_token 直接 401；带上会 302 换 Cookie（有效期 3 小时、每次部署轮换）⇒ 只能用于验证，不能作为长期入口。正式使用需在控制台绑自定义域名。
端点形态 单一形态 支持两种 裸域名（正式）与带令牌的预览链接（需先换 Cookie）。后者让「域名还没绑好」时也能端到端验证整条链路。

C.4 一个顺带拿到的成本收益

大陆探测臂是**批量接口**：N 个站点一次调用测完，只花 1 个 CF 子请求（每个端点 1 个）；而 Globalping 是「每站点 2 个子请求」（发起 + 收取两阶段），证书检测更是每站点同步轮询十几次。
所以引入它不只是「测得更准」，还**显著降低了 CF 免费层 50 子请求上限的压力** —— 这一点在计划里没有被预见到。
